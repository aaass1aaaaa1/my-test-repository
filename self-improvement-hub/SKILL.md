# 自我改进中枢

Agent 的「记 → 炼 → 用」单一入口：捕获学习、错误与用户纠正，维护可追溯的经验账本，支持晋升项目记忆、提取为技能、每日一项的节奏化改进。

## 30 秒速查卡

```
触发捕获 → 写对账本（LRN/ERR/FEAT）→ 定期回顾 → 晋升或提取 → 每日挑一项推进
```

## 工作流

### Step 1 判定捕获触发器

以下信号出现时，进入记录流程（不需要用户说「记一下」）：

| 信号 | 写入 | 类别 |
|---|---|---|
| 命令/操作失败、报错、非零退出 | `.learnings/ERRORS.md` | — |
| 用户纠正（「不对…」「其实…」「你搞错了…」） | `.learnings/LEARNINGS.md` | `correction` |
| 用户想要缺失能力（「能不能也…」「为什么不能…」） | `.learnings/FEATURE_REQUESTS.md` | — |
| 知识过时或缺失 | `.learnings/LEARNINGS.md` | `knowledge_gap` |
| 发现更优做法 | `.learnings/LEARNINGS.md` | `best_practice` |
| 非显而易见的发现 | `.learnings/LEARNINGS.md` | `insight` |

**先搜后写**：记录前搜索 `.learnings/`，已有相似条目就补 `参见` 关联并升级优先级，不重复新建。

**账本位置**：默认当前项目/工作区根目录 `.learnings/`；环境已有记忆体系（如 `.workbuddy/memory/`）或用户指定路径时从其指定，不静默更换。首次使用前确认三个账本文件存在（不存在则按 `references/learning-formats.md` 的表头创建，已存在则不覆盖）。

### Step 2 记录条目

按 `references/learning-formats.md` 的完整格式写入，硬性要求：

- **ID 规则**：`LRN-YYYYMMDD-XXX` / `ERR-YYYYMMDD-XXX` / `FEAT-YYYYMMDD-XXX`。
- **必填字段**：记录时间、优先级、状态（初始 `pending`）、领域、摘要、详情、建议行动。
- **摘要优先**：默认只写简短摘要；**严禁**记录密钥、令牌、私钥、环境变量值或完整命令输出中的敏感段。
- **置信度不足**：内容信息不全时，对应字段写 `[需核实:字段名]` 占位，严禁编造（门控规则见 `references/confidence-gating.md`）。
- **即时记录**：上下文最清晰时立刻写入，不拖到会话结束。

### Step 3 定期回顾

开始新的重大任务前、进入有过往记录的代码/技能区域时、或每周一次，执行回顾：

1. 统计 `pending` 条目，列出高优先级项。
2. 已修复的条目：状态改为 `resolved`，追加「解决记录」（时间、Commit/PR、备注）。
3. 决定不处理的：状态 `wont_fix` 并在解决记录中说明原因，不静默挂账。
4. 相似条目互相挂 `参见`；重复出现（`出现次数 >= 3` 或跨 2 个以上任务）的升级优先级。

### Step 4 晋升与提取

满足任一条件时，把经验从账本提炼出去：

| 去向 | 条件 | 动作 |
|---|---|---|
| 项目记忆（`AGENTS.md` / `MEMORY.md` / 环境既有规则文件） | 跨多个文件/功能适用、协作者都应知道、能防止重复犯错 | 蒸馏为一条可执行规则，追加到目标文件；原条目状态改 `promoted` 并标注去向 |
| 独立技能 | 重复出现（`参见` 指向 2+ 相似问题）且已有 resolved 修复、或用户明说「保存为技能」 | 按技能创建规范生成 SKILL.md；原条目状态改 `promoted_to_skill` 并标注技能路径 |
| 技术债工单 | 系统性架构问题 | 建工单，条目注明工单号 |

**晋升要克制**：仅将经多次验证、跨场景适用的规则写入长期记忆；单次、局部、未验证的经验留在账本里。

### Step 5 每日节奏（可选模式）

用户要求「每天改进一点 / 从待办里挑一项」时启用：

1. 读取改进待办（默认 `references/improvement-backlog.md`，用户可指定位置）。
2. 挑 1 项当天可完成的：优先「待处理 + 当天可完成」，同级取优先级高（P0>P1>P2）的，再并列取最久未推进的。待办为空或全是示例时，提示用户先补真实待办，不强行编造。
3. 对选中项输出三件套：**执行步骤**（具体到命令/文件/工具）、**验证方式**（可量化的验收标准）、**记录模板**（可直接填写的当日记录格式）。
4. **只给方案，不落地改动**——是否执行由用户决定。
5. 用户执行后，结果追加到改进日志（每日一条，追加不覆盖）；每周末汇总复盘：本周完成项、搁置项及原因、下周方向。

## 边界与红线

- **受控改进（最高红线）**：本技能默认只「记录 + 提案」，不自主改写技能、规则、提示词或权重。任何晋升/提取动作都是提案，经用户确认后才落盘；`promoted` / `promoted_to_skill` 状态只有在写入真实发生后才能标。
- **改进留痕**：每次晋升/提取前，先在账本留下条目记录（改了什么、为什么、依据哪几条经验），保证任何长期记忆的变更可追溯到具体教训。
- **不覆盖已有内容**：只追加条目；初始化账本时不覆盖已有文件。
- **不记录敏感信息**：密钥、令牌、私钥、环境变量、完整命令输出中的敏感段，一律不写入账本。
- **缺失就问**：账本位置、待办内容等关键信息缺失时问一次，不猜。
- **定期清理**：过期条目及时关闭（`resolved` / `wont_fix`），不让账本无限膨胀。
- **风险意识**：账本会被未来会话读取，错误信息被固化等于持续投毒——记录时确保「正确做法」经过验证。

## 反模式（看到就躲开）

| 反模式 | 问题 | 正确做法 |
|---|---|---|
| 过度泛化 | 从单条经验提炼普适结论 | 至少 3 条同类记录才提炼通用模式 |
| 编造信息 | 经验里没有的内容被脑补进去 | 用 `[需核实:字段名]` 占位 |
| 只记成功 | 失败案例不入账 | 错误与成功同等记录，正反经验都留 |
| 摘要写虚 | 「进一步调查」「以后注意」这类空话 | 写具体可操作的下一步，带文件/命令/条件 |
| 静默晋升 | 未经确认直接改长期记忆 | 先提案、经确认、再落盘、后标状态 |

## 输出规范

- 格式：Markdown；账本条目按 `references/learning-formats.md` 的模板写，汇报用逐项列表。
- 结构：结论先行 → 记录了什么 → 建议的后续动作（晋升/提取/关闭）。
- 语气：极简、直接；条目摘要必须是未来 Agent 不用翻上下文就能看懂的句子。

## 示例

**示例 1：错误捕获 → 排障经验**

输入（场景：`git push` 报错）：

```
remote: Permission to aaass1aaaaa1/my-test-repository.git denied
```

输出（节选，写入 `.learnings/ERRORS.md`）：

```markdown
## [ERR-20261015-001] git_push_permission_denied

**记录时间**: 2026-10-15T01:30:00+08:00
**优先级**: high
**状态**: pending
**领域**: config

### 摘要
git push 被拒：GitHub 集成对目标仓库只有只读权限。
### 建议修复
改用有 repo 写权限的 PAT，或在 GitHub App 设置里给仓库开写权限。
### 元数据
- 可复现: yes
```

**示例 2：用户纠正 → 晋升规则**

用户说「不对，以后会议纪要先给结论再给细节」→ 写入 `LEARNINGS.md`（`correction`）→ 该规则跨场景适用，蒸馏为一条写入 `MEMORY.md`，原条目标 `promoted`。

**示例 3：每日一项**

用户说「今天改进什么」→ 读待办 → 选中「给技能包补 README」→ 输出三件套（步骤：写哪几节；验证：上传后渲染正常；记录模板）→ 等用户确认执行。

## 交付要求

- 账本条目必须落盘到 `.learnings/`（或用户指定路径），不只贴代码到对话。
- 晋升、提取、每日方案的产出，都先给用户过目，确认后再写入长期位置。
