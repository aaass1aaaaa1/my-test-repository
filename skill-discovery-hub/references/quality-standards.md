# 技能质量评估标准与反模式

## 六维打分

拿到一个候选技能，按这六项过一遍。**任何一项不及格就换一个**——技能生态里选择很多，没必要将就。

### 1. 真实用例

- 好：解决一个具体的、有人真的会反复做的事。
- 差：演示性质、玩具、为了展示技能机制而造的。

判断法：能不能一句话说清「谁会在什么时候用它」？说不清就是演示品。

### 2. 可移植性

- 好：遵循 Agent Skills 开放标准，文件夹结构标准，跨 Agent 可用。
- 差：绑定单一平台、含私有注解、只能在某个客户端跑。

判断法：把文件夹原样拷到另一个 Agent 环境，能用吗？

### 3. 依赖

- 好：零依赖，或依赖明确列出且可安装。
- 差：隐式依赖，装完跑不起来，报错信息看不懂。

判断法：`scripts/` 里的脚本在无额外安装的环境能跑吗？

### 4. 产出可验证

- 好：有明确产出物与验收方式（生成了什么、怎么算对）。
- 差：「帮你优化一下」「让代码更好」——无法判定是否完成。

判断法：跑完之后，能不能明确说「做完了 / 没做完」？

### 5. 描述质量

- 好：说清**做什么 + 什么时候用**，含用户真实说法。
- 差：只有形容词，或只写技术名词。

判断法：把 description 给一个不了解的人看，他知道什么时候该触发吗？

### 6. 触发精度

- 好：该触发时触发，不该触发时安静。
- 差：什么请求都跳出来（过度触发比不触发更烦）。

判断法：用 3 个相关句 + 3 个无关句测试。

## 常见反模式（推荐与安装场景）

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 看到推荐就装，不看依赖和文档 | 装完跑不起来，或与其他技能抢触发 | 先查重、看描述、确认适用场景再装 |
| 把推荐结果当质量担保 | 推荐只反映相关度匹配，不含来源权威性 | 对高置信度结果仍人工抽查原始描述 |
| 跳过验证直接使用 | 未经验证的技能可能不符合预期 | 装后跑一遍真实用例，跑不通就换 |
| 同一领域装多个重叠技能 | 互相抢触发，行为不稳定 | 一域一主力，其余卸载 |
| 用「帮我处理一下」这类模糊输入做决策 | 意图误判，装错技能 | 要求用户补全功能对象与场景 |

## 自建技能的贡献规范

找不到合适的，就自己做一个。规范：

1. **基于真实用例**——你或别人真的会用到。
2. **先查重**——确认没有已有技能覆盖同一件事（在官方库、社区索引、市场都搜一遍）。
3. **遵循结构模板**——`SKILL.md` + 可选 `references/`、`scripts/`；frontmatter 必填 `description`、`description_zh`、`description_en`、`version`、`author`，`name` 为 kebab-case 且与目录名一致。
4. **跨平台测试**——至少在两个 Agent 环境验证能跑。
5. **文档清晰**——写清定位、触发条件、用法、边界（不适用于什么）。

## 装好之后的维护纪律

- 记录每个技能的用途与启用时间，便于回溯。
- 同一领域保留一个主力，其余卸载——多个技能会**互相抢触发**。
- 季度清理：三个月没用过的，大概率不会再用了，卸载。
