# 提示词优化六步法

适用于各类提示词：系统提示词、任务指令、Agent 指令、SKILL.md 正文段落。目标是把"能跑"改成"稳定跑对"。

## 第 1 步：意图澄清

先问三个问题，答案不明就问用户，不猜：

1. **目标**：这段提示词最终要产出什么？判断成功的标准是什么？
2. **失败模式**：现在它错在哪？答非所问、格式不稳、太长、太短、胡编？
3. **约束**：哪些东西不能改（术语、语气、输出格式、目标受众）？

不同失败模式对应不同处方，先定位再动手：

| 失败模式 | 主要处方 |
|---|---|
| 答非所问 | 第 1 步 + 第 3 步 |
| 格式不稳 | 第 4 步 + 第 3 步 |
| 输出过长/过短 | 第 3 步（显式长度约束） |
| 胡编乱造 | 第 3 步（知识边界与引用要求）+ 第 5 步 |
| 时好时坏 | 第 2 步 + 第 4 步 |
| 边界崩溃 | 第 5 步 |

## 第 2 步：结构分层

把一大段文字拆成清晰区块，用 Markdown 标题或分隔符。推荐骨架：

```
# 角色
一句话定位，含领域与身份

# 任务
要完成的具体事情

# 输入
会收到什么，格式如何

# 步骤
1. ...
2. ...

# 约束
- 必须...
- 禁止...

# 输出格式
明确的格式定义或模板

# 示例
输入 → 输出 对照

# 边界
什么情况不执行 / 失败如何降级
```

模型对结构化文本的遵循度显著高于连续段落。原提示词若是一整段，仅做结构化这一步通常就能提升稳定性。

## 第 3 步：约束显式化

把隐含假设写成明规则。检查清单：

- [ ] **长度**：字数、段数、条目数是否明确？"简洁"→"不超过 200 字"
- [ ] **语气**：正式/口语、是否用 emoji、人称
- [ ] **格式**：Markdown / JSON / 纯文本，字段名与层级
- [ ] **知识边界**：能否使用外部知识？不确定时如何处理？
- [ ] **禁止项**：明确列出不要做什么（不要编造、不要重复问题、不要道歉式开场）
- [ ] **优先级**：约束冲突时谁优先（如"格式优先于详尽度"）

反面示例 → 正面示例：

- "尽量简洁" → "全文不超过 300 字，单段不超过 3 句"
- "专业一点" → "使用行业术语，避免口语化表达，不出现'大概''可能'等模糊词"
- "处理好边界情况" → "输入为空时回复'请提供具体内容'并停止后续处理"

## 第 4 步：示例注入

Few-shot 是提升稳定性最有效的手段之一。规则：

- 至少 1 组完整「输入 → 输出」对照
- 示例要真实、贴近实际使用场景，不用占位符玩具数据
- 覆盖一个典型场景 + 一个边界场景（如输入缺失、格式异常）
- 示例风格必须与期望输出完全一致——模型会模仿示例的语气和密度
- 若提示词较长，示例放在靠后位置；若较短，放在靠前位置

## 第 5 步：边界与失败处理

补三类规则：

1. **不适用场景**：明确写出哪些请求应当拒绝或转交，如"不回答与本任务无关的问题"。
2. **输入缺失**：缺关键信息时是提问还是按默认值处理？写清楚。
3. **执行失败**：中途失败如何降级？是部分交付 + 说明，还是报错停止？

模板句：

```
若输入缺失关键字段 <X>，先用一句话询问，不要自行推测。
若执行到步骤 N 失败，输出已完成部分并说明失败原因，不要静默跳过。
不处理 <Y> 类请求，遇到时回复"本提示词不覆盖该场景"并说明原因。
```

## 第 6 步：冗余压缩

删掉不产生行为差异的文字。常见可删项：

- 客套与礼貌用语（"请你好好想一想""非常感谢"）
- 重复强调的同一约束（说一次足够，重复反而稀释权重）
- 抽象的能力描述（"你很聪明""你是专家"——不指导行为）
- 与任务无关的角色包装
- 已被示例覆盖的文字说明

压缩原则：**保留所有改变行为的词，删除所有不改变行为的词**。

## 输出格式

给用户三样东西：

1. **改写后的完整提示词**（可直接复制）
2. **变更说明表**：改了什么 → 为什么 → 预期收益
3. **A/B 版本**（可选）：保守版（小改）与激进版（重构），让用户按风险偏好选

## 升级判断

改写过程中若发现这段提示词具备以下特征，主动提示用户"这更适合封装成技能"：

- 需要长篇参考资料支撑
- 需要执行确定性脚本
- 需要输出模板文件
- 会被反复使用且每次都要重新粘贴

此时转主线 A，走 `references/creation-workflow.md`。
