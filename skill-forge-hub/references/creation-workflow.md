# 新建技能七步法

## 第 0 步：判断该不该做成技能

适合封装的信号：

- 用户反复做同一件事，每次都要重新交代背景
- 流程有门道，重来一次容易踩同一个坑
- 输出有格式标准，AI 每次自由发挥都不达标
- 需要领域知识或固定参考资料支撑

不适合封装的信号：

- 一次性任务，做完不再重复
- 没有稳定流程，每次做法都不一样
- 纯知识问答，不需要执行步骤

判为不适合时直接告诉用户，别硬做。

## 第 1 步：五项需求澄清

一次问清，不要挤牙膏式追问。核心五问：

1. **做什么**：这个技能要完成的具体任务是什么？输入什么、输出什么？
2. **何时用**：用户会怎么说出这个需求？列 3–5 句真实说法。
3. **硬标准**：有没有必须遵守的格式、规范、字段、术语？给样例。
4. **边界**：什么情况不该用？失败了怎么办？
5. **依赖**：需要外部工具、API Key、特定运行环境吗？

第 2 问最关键——它直接决定 `description` 的触发词质量。

## 第 2 步：命名

- `name`：kebab-case，与目录名一致，3–64 字符。命名公式：`细分场景 + 核心动作`，如 `weekly-report-generator`、`pdf-editor`。
- `display_name`：中文展示名，8–15 个汉字为宜。命名公式：`细分场景 + 核心动作 + 定位`，如「金融材料风险解析与洞察助手」。
- 校验正则：`^[a-z0-9]+(-[a-z0-9]+)*$`

## 第 3 步：写 description 三段式

```
第一段：核心能力——输入什么 → 输出什么
第二段：适用场景——≥2 个具体场景，分号分隔
第三段：触发词——≥6 个，分号分隔，覆盖用户自然表达
```

触发词来源优先级：

1. 用户第 1 步亲口说的说法（最真实）
2. 同类任务的常见动词：生成、解析、转换、整理、检查、优化、对比
3. 领域黑话与缩写
4. 常见错拼与口语表达

写完读 `references/description-crafting.md` 做一次打磨。

## 第 4 步：搭正文骨架

从 `assets/SKILL-template.md` 起手。正文推荐结构：

| 章节 | 内容 |
|---|---|
| `# 技能名` | 一句话角色定位 |
| `## 工作流` | 分步骤，每步说清做什么、用什么工具、产出什么 |
| `## 判断规则` | 分支条件与路由逻辑 |
| `## 边界与例外` | 什么情况不执行、失败如何降级 |
| `## 输出规范` | 格式、字段、语气、长度 |
| `## 资源索引` | 指向 references / scripts / assets 的表格 |
| `## 交付要求` | 落盘还是对话输出、是否需校验 |

写法纪律：

- 动词开头的祈使句，不写"你应该…"
- 每步指明工具，如"用 Read 读取…"、"执行 scripts/xxx.py…"
- 能举例的地方给可复制的例子
- 控制在 500 行以内，超出就下沉到 references

## 第 5 步：分配资源层

| 内容类型 | 放哪里 | 判断依据 |
|---|---|---|
| 需要确定性执行、会被反复重写的逻辑 | `scripts/` | 交给代码比交给模型可靠 |
| 长篇规范、schema、API 文档、案例库 | `references/` | 按需加载，不占常驻上下文 |
| 输出模板、样板代码、图标字体 | `assets/` | 直接复制进产出物 |

避免重复：同一份规范要么在 SKILL.md，要么在 references，不要两处都写（会漂移）。

## 第 6 步：自检

```
python3 scripts/validate_skill.py <技能目录>
```

逐项看报告：BLOCK 项必须清零，WARN 项评估后决定，INFO 项按需采纳。修完再跑一次。

## 第 7 步：补上架信息

- 复制 `assets/manifest-template.yaml` 填好 name、display_name、description（中英）、category、version、author、slug、tags、触发词
- 写 2–5 条推荐问题（试试这样问我），中英各一套
- 打包 zip，根目录为技能文件夹

## 交付前的最后两问

1. 把 `description` 单独抽出来给一个没读过正文的模型看，它能否判断出该不该触发？
2. 用户最可能说错的那种说法，能不能触发？
