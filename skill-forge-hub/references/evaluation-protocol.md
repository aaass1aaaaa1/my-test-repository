# 技能评估协议

用户提出「评估 / 测评 / 评测 / 比较效果 / 有 skill 和没 skill 谁更好」时启用。核心纪律：**先对齐，再执行**——评估的成败一半在标准，不在跑分。

## 第一段：前置对齐（必经，不可跳过）

第一次收到评估请求时，只允许走到提案阶段：

1. **判型**：这个技能的评估带不带主观性？
   - 客观型（输出可程序化判定，如格式校验、字段完整性）→ 可直接推荐自动评法。
   - 主观型（人格模仿、语气风格、方法论借用、多技能横向比较）→ 必须先做判型说明。
2. **给评法选项**：列出可选评法（如 with-vs-without 对比、A/B 双盲、基准测试集、专家评审），说明各自适用场景与成本。
3. **等拍板**：只有用户明确说「按这个标准评」，才进入第二段。用户没确认前，不给分、不宣布谁更好、不开始跑任何对比。

## 第二段：正式执行（用户拍板后）

1. 按对齐的计划执行，评法不中途降级为「聊天结论」。
2. 每个样本记录：输入、输出、评分依据（引用了计划里的哪条标准）。
3. 评分必须可追溯：每个分数能对应到具体证据，不写「感觉更好」。
4. 中途发现计划有漏洞 → 停下来重新对齐，不硬跑。

## 第三段：结论

- 结论先行：哪个更好 / 是否值得改 / 改哪里。
- 附证据摘要与样本量；样本不足时明说「证据不足以下结论」。
- 给出下一步建议（改结构 / 改 description / 不动），不夹带达成结论手段之外的改动。

## 红线

- 默认路径要轻：没有评估意图时，不要主动发起 benchmark 或 A/B 对比。
- 不用评估流程替代结构改造：评估发现「触发不准」时，修的是 description；发现「执行跑偏」时，修的是 workflow——两者不互相顶着用。
- 不为了评估创建 `evals/`、workspace 等重资产；用户要闭环时才建。
- 进入任何重型对比前，先复述一次 `current_path` / `current_step` / `next_action`，确认不是惯性把任务拉进了重路径。
