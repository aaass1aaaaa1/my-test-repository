# description 与触发词打磨

`description` 是技能唯一的"广告位"——模型靠这一行决定是否触发。写不好，正文再精彩也不会被加载。

## 三段式模板

```
<核心能力：输入 → 输出>。适用场景：<场景A>；<场景B>；<场景C>。触发词：<词1>；<词2>；<词3>；<词4>；<词5>；<词6>。
```

拆解：

| 段 | 作用 | 量化要求 |
|---|---|---|
| 核心能力 | 让模型理解技能边界 | 一句话说清输入与输出 |
| 适用场景 | 提供语义匹配的锚点 | ≥ 2 个，建议 3 个，分号分隔 |
| 触发词 | 覆盖用户自然表达 | ≥ 6 个，建议 8–12 个 |

总长控制在 1024 字符内，中文建议 150–350 字。

## 触发词的四层来源

1. **用户原话**：第 1 步需求澄清时用户亲口说的说法，最真实，必收。
2. **任务动词**：生成、创建、解析、转换、整理、检查、优化、对比、提取、改写、诊断、排版。
3. **领域术语与缩写**：如 SKILL.md、frontmatter、SemVer、kebab-case、prompt。
4. **口语与错拼**：如"搞个技能""写个 skill""提示词改一下"。

常见错误：只写书面术语，不写口语表达。用户不会说"我需要执行技能工程任务"，他会说"帮我做个技能"。

## 打磨五问

写完对着问一遍：

1. **能不能反向排除？** 描述里是否隐含了不该触发的场景？必要时加一句"不用于…"。
2. **有没有近义技能冲突？** 若市场存在描述高度相似的技能，要突出差异点（如"专注中文排版"）。
3. **触发词够不够"土"？** 把最学术的词换成用户真会说的说法再试。
4. **中英文语义一致吗？** `description_zh` 与 `description_en` 必须表达同一能力，不能各自发挥。
5. **有没有堆砌？** 触发词不是越多越好，堆 30 个无关词会稀释语义，反而降低命中。

## 改写对照

**差**：

```
description: 一个技能相关的助手，可以帮助用户处理技能方面的各种问题，功能强大，使用简单。
```

问题：没有输入输出、没有场景、没有触发词，"技能方面"边界模糊。

**好**：

```
description: 技能创建助手，辅助创建符合市场规范的新技能、诊断并优化已有 SKILL.md、打磨各类提示词。输入一个想法或一份现有技能/提示词，输出可上架的技能包或改写方案。适用场景：从零封装重复工作流；给已有技能做合规体检与命中率优化；把粗糙提示词改成结构化可靠指令。触发词：创建技能、技能创建助手、写个技能、做个 skill、SKILL.md、技能框架、封装流程、优化技能、技能诊断、技能体检、改写 SKILL.md、优化提示词、提示词优化、提示词改写、打磨 prompt、上架技能。
```

## 优化已有 description 的方法

当用户反馈"触发不准"时，按此顺序排查：

1. **漏触发**（该触发没触发）：补触发词，尤其是口语表达；检查是否把触发条件误写进了正文。
2. **误触发**（不该触发却触发）：补反向排除句，明确"不用于…"；收敛场景描述中过宽的词。
3. **触发了但做不好**：这不是 description 的问题，转 `references/optimization-audit.md` 查正文质量。

## 版本迭代注意

改动 `description` 会直接影响命中率。建议在 manifest 中记录改动前后，观察一轮实际触发数据再决定是否继续调整。每次只改一个变量，便于归因。
